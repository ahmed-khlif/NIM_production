# UX Flows

## Production Manager

Planning opens on the earliest active scheduled event: globally on `/planning`, and within the selected Affaire or machine on its scoped Planning page. If the scope has no active scheduled event, the calendar opens on today. Changing the date manually remains in effect for the current visit.

The day and week resource timeline shows only machines with events in the selected period and current filters. A “Afficher toutes les machines” control reveals idle resources when the manager needs to inspect or plan them.

The Machines directory keeps its search field and status selector on one aligned row at desktop and tablet widths; they stack at mobile widths without clipping. The result count and reset action remain directly below the filters.

Every shared application table has manually wired, accessible column sorting. Tables with a Profile column start in ascending profile order; the Tekla import preview keeps the spreadsheet's original row order. Click a column heading to sort its displayed rows ascending; click it again to reverse the order. A manually selected column and direction override the default and persist through page changes in the current browser session. Text, numeric, and common French date values are compared by their displayed values. Selection and action columns remain non-sortable. Server-paginated piece, production-progress, and machine-bar lists also request profile-first ordering so profile groups remain consistent between pages.

The preparation demand table aggregates identical profile and length requirements into rows. Clicking any Profile, Length, or Quantity header sorts the entire table by that column; clicking the active header again reverses the direction.

In the Façonnage demand summary, each profile has a “Modifier” shortcut to the Affaire’s pieces filtered to that exact profile. Demand quantities are derived from persisted pieces; correcting them opens the source pieces so edits are validated and saved through the normal API.

The Façonnage preparation summary groups requested cut lengths under one exact profile, combining repeated profile/length rows and showing each demand as `length × quantity`. This keeps the planning review compact without hiding individual length needs.

On the Affaire overview, administrators can choose any non-archived status at any time. A confirmation explains that this changes the Affaire label only and does not reverse shop-floor or quality records. Each override is visible in append-only history; archiving stays a separate action. Production managers retain the guarded workflow actions.

The dashboard trend panel reads server-aggregated production and quality activity. Managers can select 7, 14, 30, or 90 days; the API validates the range. Loading, API error, and no-activity states remain visible, and the panel collapses responsively with the other shadcn-style charts.

Dashboard -> Pieces -> Create/Import -> Piece Detail -> Assignment Board -> Machine Queue -> Monitor -> History/Quality.

The authenticated shell provides a persisted theme toggle. Users can switch between light and dark mode from the header; the selected theme is stored locally, follows the system preference by default, and applies to shared cards, inputs, menus, dialogs, charts, and calendar surfaces.

The dashboard reads live summary metrics, machine queue/in-progress counts, piece status, unit lifecycle, priority mix, quality conformity, defect categories, treatment decisions, pending deviations, delivery risk, delayed pieces, active pieces, and recent persisted history through `/dashboard/overview`. The first row prioritizes production progress, work in progress, delivery delay, quality exceptions, and machine availability; duplicate KPI tiles are removed. Machine UI reports actual queue and in-progress counts, not a time/capacity utilization percentage (the system does not yet collect the denominator needed to calculate utilization). Status and priority are shown as labeled proportional bars instead of generic donut charts; production/quality events use unfilled daily lines to avoid overlapping area fills. The trend window is shareable through the URL, refresh time reflects the query timestamp, and quality conformity shows “—” until there is an inspection denominator. Loading/error/empty states remain explicit; the responsive layouts retain shadcn cards and chart primitives.

Offer metrics follow the production dashboard's shared KPI-card hierarchy. The Offer overview counts piece-unit states only; bar status and assignment indicators count bars only, and those measures are not combined into a single pipeline. The existing Offer Production view is unchanged; bar and assignment pages show only their own bar counts. Progress and quality alerts remain in their existing relevant views, with responsive cards and explicit loading/error states.

Production Planning is available to administrators and production managers at `/planning`, on each Affaire workspace at `/offers/:offerId/planning`, and from a machine at `/machines/:id/planning`. The global Planning shows all Affaires by default and allows filtering to one Affaire; assigned bars are grouped by Affaire, machine, then profile. The Affaire view offers a bulk scheduling Sheet: load all eligible unplanned bars for that Affaire, select all or remove bars by machine/profile, set one start time, an explicit estimated duration per bar, an optional gap, and a shared planned team. The selected Tunis date immediately shows the Affaire’s already planned bars, machines, times, and team. This is contextual information; only overlapping machine/operator slots conflict, and no date is disabled wholesale. Conflict labels identify the reserved machine or operator and the existing event/bar and time. A preview shows each bar’s slot and conflicts before confirmation. Bars are sequenced deterministically by machine, profile, and reference because one team is reserved for the batch; the UI never invents a production duration. Confirmation atomically saves one ScheduleEvent and audit record per bar, so each bar remains independently traceable and editable afterward. The existing single-bar form remains available for ad-hoc scheduling. Choosing a single bar opens its planning form with the current machine assignment shown and locked. The machine-row day/week timeline, month grid, and responsive mobile event list show the resulting schedule, with search and machine/operator/status filters, clickable shadcn-styled in-app calendar and 24-hour time pickers, date navigation, and paginated bar groups. Offer-specific routes open directly in that Affaire without a redundant Affaire selector, while machine routes retain the machine context. Only bars already `AFFECTEE` to their assigned machine can be scheduled. Production events collect a lead and optional helpers; maintenance and machine blocks reserve time without changing machine status. A right-side shadcn Sheet creates or edits events, and a detail Sheet shows the planned roster alongside the real bar status. Conflicts are rejected by the API; a scheduled bar must have its production event cancelled before its machine assignment can be removed. Cancelling keeps its audit record and never changes real production state. Date and time selections display `Africa/Tunis`; stored values are UTC.

The `/pieces` workbench presents the Tekla-facing data in a compact, horizontally scrollable table on small screens: Repère, exact Profil, Qté, Qualité, Longueur, Poids, Pds Tot, and Désignation. Search includes repère/profile/designation; the profile selector and existing status/priority filters, row selection, and pagination stay local to the persisted `/pieces` response. Manager actions open a shadcn right-side Sheet for manual add/edit, with inline validation and a read-only Poids × Qté total; duplication creates a separate server-validated piece, while archival is confirmed and preserves history. No project/affaire context is fabricated because the current data model has no Affaire entity.

For an `IN_PRODUCTION` Offer, production managers may edit business fields only on a piece whose full unit set is still `PENDING`; any piece with a shaped, assigned, started, or completed unit remains read-only. The API checks this inside a serializable transaction, records before/after values in the append-only history event, and increments the material revision. Creating, importing, duplicating, archiving, and changing a piece reference or quantity remain unavailable during production.

Import opens a three-step Tekla/CSV/Excel preview flow. Replacing a file clears any prior preview; nothing is committed until the server confirms zero invalid rows and the manager presses Importer. The server preview returns source-header mappings and the UI explicitly labels Surface as ignored, shows every row error and each non-blocking weight warning. If any row has the designation “jarret” (case-insensitive), a red alert asks the manager to verify its quantity, length, and weight before committing. After the transactional commit, piece and profile queries are refreshed. Managers can then open Profils à traiter, search exact profile/family, select family subsets or individual profiles with checked/unchecked/indeterminate parent states, and review demand aggregated from eligible PieceUnits. Façonnage includes new pending units and remakes, excludes assigned/completed/rework units, and re-reads demand on the server when optimizing. The manager enters candidate standard bar lengths and the actual saw kerf; NIM calculates the required number of bars and cut patterns without tracking on-hand stock quantities or reserving pieces. The result is an audited point-in-time estimate, not a released bar or machine order.

The Pieces list supports local status and priority filtering over the authenticated API projection, reports the filtered result count, preserves the existing global search entry point, and exposes clear/reset actions. Rows show a secure cover thumbnail and photo count when available. The import flow accepts a CSV by selection or drag-and-drop, shows server preview counters and row-level errors, and invalidates the list cache only after a successful transactional commit. Piece Detail provides explicit refresh/retry feedback and copy-reference utility without changing domain state, plus a responsive piece-photo gallery. Managers can select multiple JPEG/PNG/WebP files, see upload progress and validation errors, preview thumbnails, and remove a photo through confirmation; read-only roles can view but not mutate the gallery.

Within an Offer, manual piece creation displays the next Offer-local Repère and lets the manager leave it blank for safe server-side assignment at save time. Qualité and Désignation are optional and receive explicit defaults. The Offer overview’s recent-import list provides a confirmed removal action; it removes the import-history entry only, including for completed Affaires, while retaining all imported pieces and append-only production/audit history.

On a `READY` Affaire, managers can add manual pieces and edit pieces whose units are still `PENDING`; the server applies the same unit-state guard transactionally. Import replacement and archival remain draft-only. A piece already materialized into a bar must first be released by cancelling that unassigned, unstarted bar; assigned or started production data remains protected. In Vue générale, the status actions are shown beside “Statut de l’affaire”: managers/admins can mark a draft ready after plan validation, return a ready Affaire to draft only after active bars are removed, or close production when the server confirms all units and quality checks are resolved. `IN_PRODUCTION` is set by the first operator start. Managers/admins can use “Revenir à la validation du plan” from a draft or ready Affaire to jump to saved plans; revising a validated plan is allowed only before production and while its bars remain unassigned/unstarted. That action returns eligible pieces to pending and preserves the plan/bar movements in history. There is deliberately no manual rewind from `IN_PRODUCTION` or `COMPLETED` while production facts exist.

The Assignment Board assigns individual PieceUnits, blocks unavailable machines, and provides reassignment/removal confirmations while keeping the previous assignment visible in history. In Façonnage, managers select individual persisted bar proposals and validate a subset; only those bars and exact units become real CuttingBars/FACONNEE units. The plan remains partially validated until all proposals are validated, and its remaining units can be handled later. “Supprimer le reliquat” removes only unvalidated proposals from the active plan; validated bars remain untouched and the removal stays in append-only history. The profile-selection action bar stays sticky at the bottom while scrolling so “Continuer vers Façonnage” and the live selection totals remain accessible. `READY` Offers can continue Façonnage for still-pending units; once production starts, Façonnage is locked. The Offer workspace provides Barres and Affectations tabs for generated bars, machine assignment, and piece/bar traceability.

The Assignment Board can be refreshed as a coordinated assignments/machines projection, filtered to one machine, and reset without losing server authority. Each visible piece links to its persisted traceability page. The Machines list provides status filtering and explicit refresh/result feedback. Both status-change paths (the row action and edit sheet) warn managers before maintenance and show a persistent warning on the machine detail afterward. New bar assignments and production starts are rejected by the API while the machine is unavailable. On machine detail, managers can filter to affected bars, select individual eligible bars, or select all eligible bars on the current page, then release the selection after confirmation. Bulk release invokes the existing guarded release operation once per bar; successful releases retain assignment history and return their pieces to FACONNEE. Any bar whose state changed during the operation is reported as a partial failure for refresh and review. A bar already LANCEE cannot be released and its active run may finish; no new run can start during maintenance.

## Traceability

Login -> History -> Search/filter -> Event context -> Page through the append-only timeline.

The History page uses the persisted `HistoryEvent` stream, supports event/entity/search filters, desktop tables and mobile cards, pagination, refresh, loading/error/empty states, and role-aware access. Search can be cleared without losing pagination context, and entity or metadata references link directly back to persisted piece and machine views.

## Authentication and resilience

Login validates locally before calling `POST /auth/login`, keeps the submit action visibly busy, exposes API/network failures inline, and refreshes the authenticated user before navigating to the dashboard. The protected shell distinguishes an expired/absent session from an API or offline failure: unauthenticated users are redirected to Login, while recoverable infrastructure failures offer retry without silently discarding the session context. The login uses brief CSS-only entrance and focus feedback; the desktop security illustration has restrained ambient motion. System reduced-motion preferences disable decorative animation.

The supplied illustrations are used by context: security artwork supports Login and the maskable app icon, machine-maintenance artwork explains unavailable machine states, and production-in-progress artwork reinforces an active operator operation. Empty states keep the illustration optional so filtered/no-result states remain compact and task-focused.

The offline banner announces loss and recovery of connectivity. GET reads may use the safe service-worker cache; all non-GET API calls are blocked before network dispatch while offline and are never queued or replayed. Error, not-found, and unauthorized views provide explicit recovery paths without exposing server stack traces.

## Operator

Login -> Select Machine -> Queue -> Select Piece -> Start -> Validate Unit -> Send to Quality.
The current implementation persists one production operation per PieceUnit, keeps the operator's active operation visible, and rejects duplicate/concurrent starts server-side. The operator workspace exposes an explicit refresh, queue/status summaries, priority and piece traceability context, locks machine switching while work is active, and confirms the irreversible handoff to quality before calling the guarded completion endpoint. Successful production mutations invalidate the related production, assignment, piece, quality, dashboard, history, and notification projections. Pause/resume is intentionally deferred because it remains an open business decision.

## Quality

### Non-conformance treatment

Each rejected inspection shows its defect category, authenticated defect-photo gallery, cycle number, and current treatment. Production managers can choose rework, remake, scrap, or request a deviation; administrators can approve or reject pending deviations. Rework/remake return the unit to production with a new quality cycle, scrap is terminal, and an approved deviation accepts the unit. Upload, mutation, loading, error, and empty states remain visible in the responsive desktop/mobile experience.

Login -> Pending List -> Piece -> Conform/Non-conform -> Comment -> Confirm.

The Quality page is server-backed at PieceUnit level. It provides a searchable pending queue, responsive desktop table/mobile cards, a focused decision dialog, mandatory non-conform comments and defect categories, success/error feedback, consultation-mode guidance for read-only managers, pending/result counts, direct piece links, local decision filtering, and a recent decision history. Rejected inspections expose the defect-photo gallery and role-aware treatment workflow. Validation and disposition changes refresh the related quality, piece, dashboard, history, and notification projections.

## Admin

Login -> Users/Machines/Settings -> Create/Edit/Disable.

Profile is available from the account menu and uses the secured password-change endpoint. The password form confirms the new value locally, supports safe visibility toggles, explains the server-enforced minimum, and reports both API failures and successful session protection. Notifications are a separate recipient-targeted inbox with persisted read/unread state and direct workflow links; History remains the complete append-only audit trail.

Settings stores personal density and a preference for showing the unread badge through `/settings`; hiding the badge never disables inbox delivery. The notification center reads persisted recipient-owned records, filters by event and unread state, supports single and bulk read acknowledgements, and links to the related Affaire, production, or quality workflow. The header previews the newest five and displays the server unread count. New notifications are created transactionally with business history events; legacy history is not backfilled. The web shell exposes an offline banner and safe read-only cache foundation; notification read mutations are disabled offline like other writes.

User administration supports local search/status filtering, result counts, refresh and reset controls, responsive table/card layouts, guarded create/edit/password-reset flows, and explicit confirmation before account state changes. Server authorization, validation, persistence, session revocation, and audit events remain the source of truth.

The authenticated shell exposes a persistent global search field; `Ctrl+K`/`⌘K` focuses it, and submitting a query opens the full results page. The shell also shows the persisted unread-notification count, an accurate role label, keyboard-visible focus states, and responsive navigation through the shadcn Sheet on small screens.

The shared header shows a search icon. Clicking it opens a compact search field directly beneath the icon; submitting the query opens the dedicated `/search` results page. On `/search`, the icon focuses the page's existing search field instead of opening a second panel over the results. Results cover Affaires, pieces, machines, and production bars through existing server-filtered endpoints; each category is independently paginated, loading, partial-failure, and empty states are shown, and each result opens its record directly. The submitted query stays scoped to the search page, so it does not follow the user into another list.

The primary sidebar keeps the Pièces workflow in one accessible collapsible group: Liste des pièces, Importer Tekla, and Profils à traiter. It opens automatically on Pièces routes, marks only the current destination active, and keeps import/preparation links visible only to administrators and production managers. The mobile Sheet uses the same navigation; server-side guards remain authoritative.

In a non-archived Affaire's Pièces list, managers can select deletable pending pieces from every page matching the current search and profile filter. Selection remains intact while paging; changing the search or profile starts a new selection scope. The select-all control loads the filtered result pages in bounded groups, then deletion sends batches of at most 100 IDs to the API. Each API batch is atomic: if one batch fails, completed batches stay deleted and failed plus unattempted pieces remain selected for review and retry. An unvalidated draft cutting plan is invalidated and its proposal links are cleared when a pending piece is deleted; proposals in a partially validated plan remain protected until the manager cancels its remainder. The UI explains why a piece is ineligible. Append-only audit history remains available after piece rows and attached images are removed.

The desktop sidebar is pinned to the viewport: the brand and account controls remain visible while its navigation list scrolls independently. On mobile, the navigation remains scrollable inside the Sheet. When an Offer is open, the Offres group expands to show that Offer's Overview, Pieces, Tekla import, Façonnage, Production, Quality, and History routes; the active section is highlighted, and section visibility follows the same role rules as the Offer workspace tabs. The Offer workspace keeps its in-page tabs as a second, contextual navigation path.

On desktop, the sidebar remains fixed to the viewport during page scrolling; long navigation scrolls inside the sidebar, with the logo and account footer kept visible. The scrollbar is visually hidden to avoid appearing/disappearing when Pièces expands. The mobile drawer remains independently scrollable.

## Operator account and tablet flow

An administrator creates one normal application account with role `OPERATOR` in the shared Users page. The account's role, username, display name, and lifecycle are not duplicated in a separate operator directory. Tablet sign-in creates a separate short-lived tablet session, but machine membership, production runs, and audit history all use that account's existing User ID.

Current tablet access replaces the historical one-time-key flow: the operator signs in with their existing username and password. Operators cannot change their password themselves; the API enforces this and the profile page directs them to an administrator. Production managers start from Affaires in production and use each Affaire's Production tab; admins have the global `/production` monitor. See [Operator account access and production roles](OPERATOR_ACCOUNT_ACCESS.md) for the current permission and migration details.

The operator experience is intentionally outside the manager sidebar: `/production/login` → active machine selection → optional helper selection → temporary session → buttons for the Affaires with bars assigned to that machine → one selected Affaire’s queue grouped by profile and ordered by bar reference → start confirmation → running bar with elapsed timer → optional per-piece NC report → finish confirmation. The API validates the selected Affaire against active machine assignments and paginates its queue in profile/reference order. A running bar can be resumed after refresh. Ending a session is blocked while a run remains active. Server-confirmed state is required before the UI presents success; network failures offer explicit retry.

# Façonnage revisions and production monitoring

On an Offer's Façonnage page, the selected detailed profiles determine the profile cards and demand. Profile spellings that differ only by case/spacing are grouped, and active catalogue designations and aliases display under the catalogue’s canonical designation; the catalogue badge identifies that canonical match, not a separate catalogue entry for every spelling. For each profile, configure one or more raw lengths; an optional quantity caps how many bars of that length this calculation may use (blank is unlimited; it is not an inventory reservation). The panel offers click-to-add raw-length suggestions derived from each selected piece length (piece length plus 100 mm, rounded up to 500 mm); these are calculation candidates, not confirmed stock, and must be checked against material actually available. Remove any row before calculating. Results group identical cut patterns into a single motif with a count badge. Individual proposals remain separately selectable for validation.

Managers may revise a fully validated plan while its bars remain façonnée and unassigned. The confirmation explains that the bars will be cancelled, their pieces released to pending, and history retained; assigned bars must first be unassigned, and started work cannot be reset.

The Offer Production "Avancement par pièce" table has sticky search/status controls and server-side pagination. It defaults to "Affectées" (ASSIGNED); users can choose other statuses. Search accepts piece reference/profile. The table result count follows filters while the production KPI totals remain scoped to the whole Offer. Data tables share stronger header contrast, consistent row rhythm, zebra striping, and hover feedback.

Workshop non-conformity reports and formal quality checks are separate lifecycle queues. An open operator report stays visible in the Quality page's "Signalements atelier" tab while fabrication is active; after fabrication, the unit enters "À traiter" for a formal controller decision. An Affaire-specific Quality page shows an open-report alert and a direct jump to its scoped workshop queue, so reports are not mistaken for missing quality tasks. Operators may work alone (helpers are optional); their report comment should identify the defect location, observed measurement, or practical context and is shown in the Affaire's quality queue.

Across Affaire detail tabs, the Affaire summary/navigation stays pinned below the application header while scrolling. Table search and filter controls stack directly beneath the measured (responsive) Affaire tab header, avoiding overlap on narrow screens. These controls remain inside their table card so they stop with the table rather than covering unrelated page content; the Production monitor filters are placed in the table content region to preserve that sticky scope.

Piece create/edit fields for profile, quality, and designation offer suggestions computed from the selected Affaire's persisted pieces (across all pages), while remaining free-text so new values can be entered. Affaire create/edit suggests existing client and site values from server-provided facets; choosing a suggestion is optional, and custom values remain supported.

Settings makes the admin-only material catalogue a prominent “Référentiel matière” card with a direct “Ouvrir le catalogue” action; it manages canonical profile designations, aliases, kg/m weights, and raw lengths. The designation is the catalogue identity used for matching and display; aliases recognize alternate names during imports. The catalogue has no separate reference field.

Piece profile selection also searches the shared material catalogue. Selecting a catalogued profile fills the editable Poids linéique (kg/m) field with its saved kg/m and displays its available raw lengths. Total weight is calculated from kg/m × piece length × quantity; the API stores the resulting actual unit weight in kg while preserving a manual kg/m override. The admin-only catalogue is under Settings → Catalogue des profils. Each profile has a unique canonical designation, up to 30 aliases, line weight, and up to 12 available raw lengths. During piece import, an active canonical designation or alias is resolved to the catalogue’s canonical designation. Legacy workbooks with an extra “Référence” column remain importable; that column is ignored. Alias/canonical name collisions are rejected, and catalogue history records designation, alias, weight, length, and status changes. Façonnage preloads the selected profiles' raw lengths; those rows remain editable, removable, and extendable, with optional quantities serving only as a per-optimization cap—not a stock reservation.

When manually adding pieces inside an Affaire, users can add multiple cut-length rows for the same profile. Each row has its own length and quantity, shares the selected profile/quality/designation and editable kg/m, and displays its calculated weight. Saving creates one separately numbered piece per length in a single authorized, validated API transaction (up to 50 rows), preserving piece-level traceability and preventing partial batch saves.

Search and filter toolbars for the global operational tables (Affaires, pieces, assignments, machines, quality, history, notifications, and users) remain pinned below the manager header. Planning keeps its calendar filters visible while navigating the calendar; the operator tablet queue uses its own offset beneath the shorter tablet header. Façonnage's profile search/family selection toolbar is also sticky and adapts its offset when opened within an Affaire.

The Façonnage workspace is progressive rather than a long combined form: profile families containing selected catalogue profiles start expanded; families with no selected catalogue profiles start collapsed, and users can expand or collapse any family. The search and family filters share a compact sticky toolbar, and the redundant “Besoins par profil et longueur” table is omitted. Raw-length profile cards are stacked one per row and use a single-open accordion: the first selected profile starts expanded, while the others stay closed; opening another profile closes the current one. Calculated length suggestions stay collapsed until requested. Once optimization succeeds, the configuration form is replaced by one recommended-plan section containing the collapsible profile result cards, cutting diagrams, and bar-selection checkboxes. The duplicate standalone bar-validation list and redundant third-step validation panel are omitted. Proposed bars are checked by default; each profile checkbox selects or clears its remaining bars, and the global selector applies to all bars matching the search. Expanding a profile reveals each individual bar and its cut diagram with its own checkbox. A sticky action bar shows the selected count and a single “Créer les barres sélectionnées” action. This invokes the audited server operation that materializes only selected bars; unchecked proposals remain available for later. After all bars are created, the next action links directly to bar assignments. Returning to configuration or recalculating remains explicit; the saved-plan history is preserved separately.

The “Imprimer le rapport matière” action on an Affaire’s Barres page opens a compact portrait report grouped by profile and raw length. It shows required raw weight using catalogue kg/m and waste as a percentage, omits per-bar reference lists and cut-by-cut detail, and excludes cancelled bars. Profiles without a catalogue weight are identified and excluded from the calculated weight total.

Administrators can rename a material profile from its edit form. The API normalizes and validates the new designation, rejects names that collide with another catalogue profile, updates the normalized lookup key, and records old/new values in the append-only history event. Existing pieces retain the profile text saved when they were created; the rename changes the catalogue designation for future selection and matching.

# Client directory workflow

The directory filter selects active, archived, or all clients and combines with the name/fiscal-ID search. PDF print and Excel export include every matching record across all result pages, not only the currently visible page.

`Clients` in the primary navigation opens the shared directory for administrators and production managers. Search/paginate records, add or edit the legal name, fiscal identifier, up to three phones and two e-mails, and add/replace one client image from its detail page. The detail page has a print-optimized A4 layout the user can save as PDF. Admins can archive/restore clients; archiving hides the record from new Affaires while existing Affaires retain the relationship and history. Records are not hard-deleted.

When creating or editing an Affaire, choose a client from the server-backed selector or open the full client form from Nouveau client. New client records require a legal name, fiscal identifier, one telephone number, and one e-mail address; additional contact fields are optional. A successfully created client is selected in the Affaire form. Upload its optional image from the client detail page. Free text cannot create a client name; the API validates the selected client ID. Existing client names were migrated into the directory and remain linked to their Affaires. The Site field uses the same keyboard-accessible suggestion pattern, drawing prior site values from the Affaire facets while still allowing new free-text site names.

Shared responsive rules keep right-side edit sheets wide enough to use on phones, left navigation sheets compact, and confirmation dialogs inset from the viewport edge. The manager shell allows long tables to scroll within their own containers instead of widening the whole application.

The Façonnage profile picker keeps search and family filters sticky while selection controls stay in the list, reducing the pinned toolbar height during long profile reviews.

## Operator presence, notifications, and run ownership

The team picker lists only active, tablet-enabled operators who are not already in another active machine session, excludes the signed-in lead, and supports name search plus select/clear for matching results. Busy or disabled operators are omitted. It marks eligible operators online or offline; offline operators remain selectable. The server rechecks account status and active-session membership transactionally when a session starts. If an operator becomes unavailable after selection, the API reports the conflict and the picker refreshes. The visible tablet page sends an authenticated heartbeat every 15 seconds, and status becomes offline after 45 seconds without one. Presence does not reserve an operator or bind them to a machine. The operator who starts the shared machine session is its lead and is the only one who can end it. Every active teammate can observe the current run and report a non-conformity, but only the operator who launched a specific bar can cancel or finish it. A machine runs one bar at a time; another teammate can start a different bar after that run has ended. The tablet header provides each operator a persisted, user-scoped notification inbox with unread counts and mark-as-read controls.

After login and machine/team selection, the tablet shows the Affaires with assigned bars. Choosing an Affaire opens only its paginated bar queue, grouped by profile. “Toutes les affaires” returns to the chooser so the operator can switch context without leaving the machine session.

The pieces workbench provides a one-tap “Jarret” designation filter. It uses an exact, case-insensitive server filter and combines with search/profile filters; clearing the filters restores the full list. The Tekla import warning remains a separate blocking verification step when imported designations contain Jarret.

On a machine in maintenance, managers can select all matching assigned, not-yet-started bars across every result page. The list retains this selection while paging and searching/status changes clear it. The maintenance bar table sends supported sort choices to the API, so the full filtered result set is ordered before pagination. The Affaire assignment picker distinguishes selecting the current page from selecting all bars matching its search; full-result selection is capped at 500 bars per assignment to match the API's atomic request limit.

The manager notification popover is anchored to the viewport on narrow screens, stays inside the safe-area bounds, and uses an independently scrollable list with touch-sized close/read actions. Tapping outside closes it; long notification text wraps without widening the page. The full notification inbox stacks its filters and date metadata on mobile.

The authenticated manager header provides a compact return control on every non-dashboard page. It returns to the previous in-app location when available and otherwise uses the route's parent page (including Affaire tabs, piece/machine/client detail, and settings subpages). Detail-page return links use the same history context to preserve filters and pagination. Tablet pages keep workflow-specific back controls: machine/team setup, selected Affaire to Affaire chooser, and bar/run details back to the production queue.

During an active machine session, its lead can open the team editor to add or remove eligible assistants at any time, except the operator who started a currently running bar. That operator remains on the team until the run is completed or cancelled so they retain authority to close their run. Membership changes are audited, new assistants are notified, and historical membership rows are retained.
